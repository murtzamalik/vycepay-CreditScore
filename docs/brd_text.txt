2. Executive Summary 
VyceScore is an advanced credit scoring engine that leverages alternative data sources to provide 
comprehensive credit risk assessments for Micro, Small, and Medium Enterprises (MSMEs) and 
individual borrowers in Kenya and emerging markets. The platform addresses the critical challenge 
of credit inaccessibility for the unbanked and underbanked population by utilizing non-traditional 
data points from digital financial transactions. 
2.1 Key Value Propositions 
0. Alternative Data Scoring: Utilizes VycePay wallet transactions, VyceTrade supply chain data, 
and compliance/identity verification to build credit profiles where traditional credit history is 
unavailable. 
1. Three-Tier API Architecture: Provides Lite, Pro, and Deep Dive APIs to serve different use 
cases from rapid pre-screening to custom model development. 
2. Explainable AI: All scoring decisions include transparent risk drivers to meet regulatory 
requirements and build user trust. 
3. Active Learning Pipeline: Continuously improves model accuracy through feedback loops 
with partner financial institutions. 
4. Regulatory Compliance: Built with data privacy, PII protection, and audit trail capabilities for 
financial services regulations. 
2.2 Target Market 
VyceScore primarily targets banks and financial institutions in Kenya evaluating loan applications and 
pre-approved loan marketing campaigns. The platform is designed for global extensibility to serve 
emerging markets with similar credit infrastructure challenges. 
2.3 Business Model 
VyceScore operates on a tiered licensing model based on query volume. Enterprise customers are 
onboarded through a sales-led process with customizable licensing terms. The platform offers 
sandbox environments for integration testing and supports white-label embedding for partner 
banks.

3. Problem Statement 
3.1 Market Context 
In Kenya and many emerging markets, a significant portion of the population and MSMEs remain 
unbanked or underbanked. Traditional credit scoring models rely heavily on formal credit history, 
which is unavailable for this segment. This creates a critical gap where creditworthy individuals and 
businesses are denied access to financial services due to lack of credit data. 
3.2 Pain Points 
3.2.1 For Financial Institutions 
1. High Default Rates: Limited visibility into borrower creditworthiness leads to higher non-
performing loan ratios. 
2. Manual Underwriting: Traditional credit assessment processes are time-consuming and 
resource-intensive. 
3. Limited Market Reach: Inability to serve the unbanked segment represents missed revenue 
opportunities. 
4. Regulatory Pressure: Increasing requirements for explainable credit decisions and fair 
lending practices. 
5. Data Fragmentation: Multiple data sources require complex integration and reconciliation. 
3.2.2 For Borrowers 
1. Credit Inaccessibility: Lack of formal credit history prevents access to loans and financial 
services. 
2. High Interest Rates: When credit is available, it comes with high interest rates due to 
perceived risk. 
3. Lengthy Approval Processes: Traditional loan applications require extensive documentation 
and long waiting periods. 
4. Opaque Decisions: Borrowers often do not understand why credit applications are rejected. 
3.3 Current State Analysis 
The current credit assessment landscape in Kenya relies primarily on: 
• 
Credit Reference Bureaus (CRBs) with limited coverage of the population 
• 
Manual document review and verification processes 
• 
Collateral-based lending that excludes asset-poor borrowers 
• 
Relationship-based lending limited to existing bank customers 

---PAGE BREAK---
3.4 Opportunity 
The proliferation of digital financial services has created a wealth of alternative data that can 
indicate creditworthiness: 
• 
Mobile money transaction patterns reveal cash flow stability 
• 
Digital payment histories demonstrate financial discipline 
• 
Supply chain relationships indicate business viability 
• 
Merchant activity data shows revenue generation capability 
VyceScore captures this opportunity by building a comprehensive credit scoring engine that 
transforms alternative data into actionable credit risk assessments.

6. Data Flow Architecture 
This section describes the complete flow of data through the VyceScore system, from source 
ingestion to score delivery. 
6.1 High-Level Data Flow 
The data flow follows an ETL (Extract, Transform, Load) pattern with additional ML inference and 
feedback loops: 
1. Data Ingestion: Raw data is extracted from source systems (VycePay, VyceTrade, Compliance 
Partners) 
2. Data Validation: Incoming data is validated for completeness, consistency, and quality 
3. Feature Engineering: Raw data is transformed into ML features and aggregated metrics 
4. Feature Storage: Engineered features are stored in the feature store for model inference 
5. Model Inference: ML models generate credit scores and risk predictions 
6. Score Storage: Generated scores are stored with timestamps for historical tracking 
7. API Delivery: Scores are delivered via REST APIs to consuming applications 
8. Feedback Collection: Actual loan outcomes are collected from partner banks 
9. Model Retraining: Production feedback is used to continuously improve models

7. High-Level Architecture 
VyceScore follows a microservices architecture designed for scalability, maintainability, and cloud-
agnostic deployment. The system is composed of loosely coupled services that communicate via 
well-defined APIs. 
7.1 Architectural Principles 
• 
Cloud-Agnostic: Deployable to any cloud provider or on-premises infrastructure 
• 
Microservices: Independent services for scalability and fault isolation 
• 
API-First: All functionality exposed through REST APIs 
• 
Event-Driven: Asynchronous processing for batch operations and feedback loops 
• 
Data Privacy: PII minimization and encryption throughout the pipeline 
7.2 System Components 
7.2.1 API Gateway 
The API Gateway is the entry point for all external requests, handling authentication, rate limiting,

12.2 Training Data Generation 
12.2.1 Phase 1: Vyce-Observed Distress (VOD) 
Initial training uses internal financial stress signals as proxy labels since formal default data is scarce 
for unbanked MSMEs. 
10. VOD Signal Definition: Internal indicators of financial distress derived from transaction 
patterns 
11. GOS Index Volatility: Sudden erratic changes in the GOS (Gross Operating Surrogate) Index 
12. CBLRI Drop: Massive cash-outs dropping the CBLRI (Core Balance Liquidity Ratio Index) 
13. Transaction Pattern Breakdown: Significant deviation from established transaction patterns 

---PAGE BREAK---
14. Label Assignment: Users exhibiting VOD signals are labeled as high-risk (positive class) 
12.2.2 VOD Signal Calculation 
# GOS Index (Gross Operating Surrogate) 
gos_index = ( 
    (incoming_tx_value_30d - outgoing_tx_value_30d) / 
    max(incoming_tx_value_30d + outgoing_tx_value_30d, 1) 
) 
 
# CBLRI (Core Balance Liquidity Ratio Index) 
cblri = ( 
    avg_daily_balance_30d / 
    max(avg_daily_balance_90d, 1) 
) 
 
# VOD Flag 
vod_flag = ( 
    (gos_index_volatility > threshold_gos) OR 
    (cblri_drop_percent > threshold_cblri) OR 
    (tx_pattern_zscore > threshold_pattern) 
) 
12.2.3 Phase 2: Production Ground Truth

15. Partner bank issues loan to user scored by VyceScore

12.4 Explainability Framework 
12.4.1 SHAP Values 
SHAP (SHapley Additive exPlanations) values provide feature-level explanations: 
• 
SHAP values indicate each feature's contribution to the prediction 
• 
Positive SHAP values increase default probability (lower score) 
• 
Negative SHAP values decrease default probability (higher score) 
• 
Values are normalized to percentage contribution for user presentation 
12.4.2 Top Risk Drivers Selection 
# Calculate absolute SHAP values 
shap_abs = abs(shap_values) 
 
# Sort features by contribution 
sorted_features = argsort(shap_abs)[::-1] 
 
# Select top 3 drivers 

---PAGE BREAK---
top_3 = sorted_features[:3] 
 
# Format for API response 
risk_drivers = [] 
for i in top_3: 
    risk_drivers.append({ 
        "factor": feature_names[i], 
        "impact": "positive" if shap_values[i] > 0 else "negative", 
        "description": generate_description(feature_names[i]), 
        "contribution": round(shap_abs[i] / sum(shap_abs) * 100) 
    })
